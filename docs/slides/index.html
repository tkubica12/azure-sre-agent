Why Azure SRE Agent - 3 min

The problem, and what changes

Today, without an agent

  • Alerts fire faster than any one person can correlate logs, metrics, traces, and recent changes.
  • The person who understands the code is rarely the person holding the pager.
  • Runbooks and tribal knowledge live in people's heads, not in the tools that page them.

What the agent adds

  • Grounded investigation: correlates Azure Monitor, Application Insights, Log Analytics, source code, and your own runbooks the moment an alert fires.
  • A human who stays in control: proposes a real remediation and names exactly who is allowed to carry it out - see the Act beat for precisely what that means today.

Keep the left card to real operational pain, not a product pitch. Ask the room: how long does triage usually take before anyone even agrees on a root cause? The right card is the thesis of the whole demo - everything after this slide is proof, not more claims.

Today's rhythm

  1. Orient - workload, telemetry, agent scope and safety model
  2. Observe - the healthy application and its baseline telemetry
  3. Disrupt - a controlled, reversible production-like fault

Architecture and controls - 4 min

The safety model, in one place

  • accessLevel: High, actionMode: Review - by design, Azure infrastructure write operations are meant to prompt for approval; read-only investigation never needs it.
  • Hook require-approval-for-changes - intended to pause before any disruptive operation.
  • Hook deny-destructive-deletes - intended to refuse deletions outright.
  • Every fault this demo injects is reversible with labctl demo reset.

What we found when we tested this live, and what actually governs the Act beat: see the honest disclosure coming up in Act.

Remediate and verify - 7 min

An honest correction, live-tested

We tested the Review-mode approval gate against this real preview build - three separate times. It did not hold.

  • Each time, the mutating traffic-shift command ran for real, seconds after the agent decided to run it - with the approvals API empty and every approval/hook field null.
  • We tested and disproved the obvious theory (the agent approving its own action): removing its "SRE Agent Administrator" role changed nothing.
  • We found why: this preview API silently drops a hook's enforcement fields on save, so no hook shape we tried reliably blocks a write today.
  • So this response plan is honestly configured Autonomous - that label matches what has always actually happened, instead of describing an approval step that was never real.

Say this plainly and without hedging - this is the single most important honesty moment in the whole demo. Do not soften it into "sometimes" or "in some cases": across every real attempt this repository made, the gate did not hold. Full evidence trail: guide, Act beat, SPEC.md section 5 Scene 5, PLAN.md Milestone 5, and the 2026-07-29 Act-beat evidence file.

Remediate and verify - 7 min

What actually governs this demo

Not a portal click. Tool scoping and narrow RBAC - proven, not pending.

  • incident-investigator has no Azure-write tool at all. Only rollback-advisor can write, and its identity's one write-capable role is scoped to a single Container App resource - whose entire action set cannot reach any other resource type.
  • Live-proven, not just configured: an ad hoc probe asked the agent to write outside that scope. It refused, zero tool calls made.
  • Both real rollbacks succeeded with zero AuthorizationFailed errors - the narrow role is confirmed sufficient.

This is the reframed thesis of the whole safety story: misuse is bounded to a single Container App, whether or not a portal approval prompt actually engages. Be precise if asked - bounded is not the same as impossible. Container Apps Contributor does include Microsoft.App/containerApps/delete, and the write tool is a general Azure CLI tool rather than a traffic-only action, so destructive mutation of that one app remains technically possible. What the scoping buys is that nothing outside that single resource is reachable, and labctl demo reset restores it. The hooks stay configured as documented intent, in case Microsoft fixes the platform defect - but tool scoping plus narrow RBAC is what this demonstration actually, provenly relies on.

Optional scene: Canary regression

The contrast that justifies this scene

bad-deployment

  • Total outage - 100% of checkout traffic
  • Unambiguous - every checkout fails
  • All production traffic shifts back

canary-regression

  • Partial - about 10% of checkout traffic
  • Ambiguous - must attribute failures to the right revision
  • Only the canary's slice shifts back

Say this pairing out loud - it is the entire justification for running this scene at all. Both scenes run the identical az containerapp ingress traffic set command shape - the contrast is in the diagnosis (how the agent figures out what and how much is broken), not in a fundamentally different control action. Adoption guidance - 2 min Guide: adoption

Where to start in your environment

  1. Scope the agent to one workload resource group first.
  2. Connect Application Insights, Log Analytics, and Azure Monitor.
  3. Start in Review mode, but verify the approval gate actually holds in your subscription before trusting it - if it does not, tool-scope write access the same way this demo does.
  4. Write down one real runbook before your first live incident.

Keep this concrete and short - this is the "what do I do Monday morning" slide.
