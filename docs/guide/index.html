Presenter guide

This guide is written directly to you, the presenter. Follow it top to bottom during rehearsal and during the live session. It matches the exact scene order in SPEC.md section 5 and the current labctl command surface.

Environment used throughout this guide (illustrative values - substitute your own subscription, tenant, and resource names before rehearsing; every ID shown here is a placeholder, not a real credential): subscription <your-subscription> (00000000-0000-0000-0000-000000000000), region swedencentral, agent sre-agent-demo in rg-sre-agent-demo, workload PulseMart in rg-sre-agent-workload-demo.

Honesty rule this guide follows throughout: no command output, screenshot, or agent response appears here unless it has been produced by a real run against this environment. Where a result is still pending rehearsal capture, that is stated explicitly instead of invented (see the Investigate beat).

Prerequisites#

  • Windows PowerShell (the supported operator platform).
  • Python 3.11+, with labctl installed in a virtual environment (labctl\.venv).
  • Azure CLI, logged in (az login) to subscription <your-subscription>.
  • GitHub CLI, logged in (gh auth login) with the repo scope.
  • config.local.toml present (copied from config.example.toml, git-ignored).

Confirm all of the above in one command before you touch anything else, from the repository root:

& 'labctl\.venv\Scripts\labctl.exe' preflight

Expected: a PASS/WARN/FAIL line per check and exit code 0. This is read-only - safe to run at the start of every rehearsal and immediately before the live session.

This guide uses & 'labctl\.venv\Scripts\labctl.exe' <command> throughout - the exact invocation form tested on this platform. A bare .\labctl\.venv\Scripts\labctl.exe works from PowerShell too; the leading & call operator is only required if you assign the path to a variable first.

Viewing these pages offline, reliably: opening these files directly as file:// URLs mostly works, but browsers sandbox localStorage per-file in some configurations, so a theme choice made in the slides may not carry over to the guide. For a rehearsal-grade setup, serve docs/ over local HTTP instead - no internet access is required or used:

python -m http.server 8000 --directory docs

then open http://localhost:8000/slides/ and http://localhost:8000/guide/ in the same browser.

Pre-show checklist#

Run this in full before any rehearsal or live session, in order, from the repository root in Windows PowerShell. It is written so a presenter who did not author this repository can execute it without guessing.

  1. Confirm the environment.

    & 'labctl\.venv\Scripts\labctl.exe' preflight
& 'labctl\.venv\Scripts\labctl.exe' verify

    Known-good expectation: preflight exits 0 with no FAIL rows; verify prints 28 passed, 0 warned, 0 failed and exits 0. If your check count differs, the agent/workload configuration has changed since this figure was recorded - read every non-PASS line before proceeding; do not rehearse against a known-bad baseline.

  2. Reset the scenario to a clean baseline.

    & 'labctl\.venv\Scripts\labctl.exe' demo prepare bad-deployment

    Confirms (and restores, if needed) 100% traffic on the known-good baseline revision and warms both /healthz and /api/checkout, so the first live request of the show is not a cold start.

  3. Pre-stage browser tabs, in this order, all signed in to subscription <your-subscription> ahead of time:

    1. The PulseMart HTTPS endpoint (checkout page).
    2. Application Insights appi-pulsemart-demo - Transaction search or Logs, ready to re-run a query.
    3. Log Analytics law-pulsemart-demo - Logs, with the KQL below already typed in but not yet run.
    4. The Azure SRE Agent portal, agent sre-agent-demo (replace the subscription-ID segment below with your own): https://sre.azure.com/#/agent/00000000-0000-0000-0000-000000000000/rg-sre-agent-demo/sre-agent-demo
    5. The Azure Activity Log for rg-sre-agent-workload-demo, filtered to Microsoft.App/containerApps write operations.

  4. Copyable KQL for the Observe and Verify beats (Log Analytics, law-pulsemart-demo):

    ContainerAppConsoleLogs_CL
| where TimeGenerated > ago(30m)
| where ContainerAppName_s =~ "ca-pulsemart-demo"
| project TimeGenerated, RevisionName_s, Log_s
| order by TimeGenerated desc
| take 50

  5. The exact grounded prompt to type at the agent for the Observe beat's live query (type this verbatim so the response is reproducibly grounded, not a leading question):

    Map the PulseMart application architecture, summarize checkout health over the last 30 minutes, and identify the currently active Container App revision.

  6. Expected portal states before you start: agent status Running; all three connectors (app-insights, log-analytics, azure-monitor) Succeeded; no open incident thread; ca-pulsemart-demo at 100% traffic on the baseline revision; alert alert-pulsemart-checkout-5xx enabled and not firing.

  7. Stop/go criteria. Go live only if every item above is confirmed. If labctl verify reports any FAIL, or the agent is not Running, or a connector is not Succeeded: stop, fix it, and re-run this checklist from the top - do not attempt to narrate around a broken baseline live.

1. Orient#

~3-4 min Segment: Why Azure SRE Agent + Architecture

Objective

Explain the workload, telemetry, agent scope, permissions, and safety model before showing anything live.

Talking points

  • PulseMart is a real FastAPI checkout service on Azure Container Apps, instrumented with OpenTelemetry.
  • The agent is deployed with accessLevel: High and actionMode: Review, which by design is meant to prompt only for Azure infrastructure write operations - read-only investigation is never gated. Say what happened when this repository tested that live in the Act beat, not here; do not resolve it early.
  • RBAC is least-privilege: see Security and safety for the exact table.
  • Two resource groups keep the agent and the workload separate for cost and cleanup clarity - see Architecture.

Command

& 'labctl\.venv\Scripts\labctl.exe' status

Expected visible state: workload deployed (endpoint, Container App, ACR, image tag, baseline revision); agent Running, access High, mode Review, model Anthropic/Automatic, connectors Succeeded; portal deep links for both resource groups.

Transition cue

"Let's see the healthy system this agent is watching." Move to Observe.

2. Observe#

~6 min (worst case 8) Segment: Healthy system exploration

Objective

Show the healthy application and its baseline telemetry, then let the agent describe it back to you unprompted by any incident.

Talking points

  • Open the PulseMart HTTPS endpoint and complete a checkout (~1 min).
  • Point out the active revision and 100% traffic weight on the status page.
  • Open Application Insights appi-pulsemart-demo (~1.5 min): request success rate, latency, and nested checkout / inventory.check / payment.charge spans.
  • Open Log Analytics law-pulsemart-demo (~1.5 min): run the copyable KQL from the pre-show checklist and show it returning rows.

Command

& 'labctl\.venv\Scripts\labctl.exe' verify

Expected: HTTP 200 on /healthz and /api/checkout, Multiple revision mode confirmed, 100% traffic on the known-good revision, real telemetry rows in both Log Analytics and Application Insights, the metric alert enabled and not currently fired, and every agent check passing.

Live: ask the agent (grounded exploration, ~2 min)

In the agent portal (deep link below - replace the subscription-ID segment with your own), type the exact grounded prompt from the pre-show checklist verbatim. Read the response aloud from the portal - do not paraphrase from memory.

https://sre.azure.com/#/agent/00000000-0000-0000-0000-000000000000/rg-sre-agent-demo/sre-agent-demo

Expected visible state: a response citing Application Insights, Log Analytics, and/or source files - proof of read-only grounded investigation before any incident exists.

Fallback

If the endpoint is cold (Container Apps scale-to-zero), reload once and narrate the brief warm-up latency as expected behavior, not a fault. If the agent's answer is slow, this is normal for a first grounded query in a session; keep talking about the architecture slide while you wait rather than going silent.

Transition cue

"Now let's give it something to actually investigate." Move to Disrupt.

3. Disrupt#

~5 min (worst case 7) Segment: Trigger and automated investigation

Objective

Inject a controlled, reversible, production-like fault and generate enough real traffic to cross the alert threshold.

Talking points

  • The bad-deployment scenario creates a new Container Apps revision from the same immutable image with DEMO_FAILURE_MODE=checkout-500 and shifts production traffic to it.
  • Multiple revision mode keeps the known-good revision available the whole time - nothing is deleted.
  • No customer or persistent data is touched; the fault only changes checkout behavior and emits structured telemetry.

Command

& 'labctl\.venv\Scripts\labctl.exe' demo trigger bad-deployment

Expected visible state: the failing revision is created and receives production traffic, synthetic checkout load runs, and checkout requests visibly start returning HTTP 500 within roughly a minute of the command completing.

Real measured alert latency

The Azure Monitor rule evaluates every minute over a trailing 5-minute window, so it can only fire on an evaluation boundary - the scenario's own honest range is 1-6 minutes, with an 8-minute bounded poll deadline before demo trigger stops waiting (it still exits 0 if the checkout failures themselves are confirmed live). All three real end-to-end runs captured in the Act-beat evidence measured trigger-to-fired at 260 seconds, 260 seconds, and 310 seconds (5m10s) - the third run, against a completely rebuilt environment, was the slowest; an earlier, separate test cycle recorded in PLAN.md Milestone 5 took over 8 minutes. Plan for the slow end, not the fast one.

Fallback

If the alert has not fired within alert.max_wait_seconds, demo trigger still exits 0 as long as the checkout requests themselves failed - the fault is genuinely live either way. Re-run & 'labctl\.venv\Scripts\labctl.exe' demo verify bad-deployment a few minutes later, or drive more load with another demo trigger bad-deployment call (idempotent - reuses the existing fault revision) rather than waiting in silence. See the Timing section's hard timebox for when to stop waiting and move on.

Transition cue

Refresh the Application Insights view from Observe live, side by side with the new failures, then move to Investigate.

4. Investigate#

~6 min (worst case 10) Segment: Trigger and automated investigation

Objective

Let the agent correlate resources, logs, metrics, alerts, source, and operational knowledge, unattended, and produce a grounded root-cause hypothesis.

Talking points

  • The fired alert routes through the AzMonitor incident platform and the checkout-5xx response plan straight to the incident-investigator subagent - no human opened a ticket.
  • It is grounded in the uploaded checkout-500 runbook, the connected tkubica12/azure-sre-agent repository, the triage-checkout-failures skill, and the investigation-guidelines/safety-rules common prompts.
  • It queries Application Insights and Log Analytics directly and correlates the failure with the new revision's configuration change.
  • incident-investigator holds no RunAzCliWriteCommands tool at all - it is structurally incapable of mutating anything. There is no platform hand-off to rollback-advisor either - this agent's workspace mode rejects new agent-to-agent hand-offs outright (live-verified; see PLAN.md Milestone 4; handoffs: [] in both subagents' configuration). What actually happens is narrower than either extreme: its written findings conclude with an explicit recommendation to engage rollback-advisor, naming the known-good revision, and that recommendation drives a Task-based subagent invocation within the same run - not a configured platform hand-off, and not a second human-initiated request either.

Real measured duration - three runs, not two

Alert fired to investigation thread created: 60s, 67s, and 47s across all three real runs (the rebuilt-environment run was actually the fastest here). Thread created to investigation report posted: 180s, 181s, and 383s (6m23s) - the third run, against a completely rebuilt environment, took more than twice as long as the first two. This is a real, measured, root-caused result (see PLAN.md's timing-drift record and the verbatim runs 1-2 transcript), not noise - do not present the faster two-run figures as typical.

Investigate is the least predictable beat in this demo. Plan for it, and turn it into content if it happens to you live. On the rebuilt-environment run, the investigation ran long for two known, root-caused reasons:

  • Three az containerapp CLI calls returned "Unknown error occurred"; the agent recovered by querying Azure Resource Graph and az rest instead, and it also initially queried Log Analytics with the wrong ID (the Application Insights app ID instead of the workspace ID) and self-corrected.
  • Every attempt to read the application source (app/pulsemart/main.py, app/pulsemart/settings.py) from the connected GitHub repository failed, because origin/main currently contains only AGENTS.md, LICENSE, and README.md - the app source was never actually committed and pushed. The agent recovered by relying on its uploaded operational knowledge documents instead and still produced an accurate, well-evidenced report.

If you see the agent's live output pause, retry, or visibly switch tools mid-investigation, say so instead of going quiet: "watch - that CLI call just failed, and it's recovering by switching to Azure Resource Graph" is a genuine credibility moment, not something to hide. This is expected to improve once the application source is actually committed and pushed to the connected repository - but no faster number has been measured yet, so do not promise a specific improved time; keep using the documented 12-18 minute range until a faster run is actually recorded.

Expected visible state

An open incident in the agent portal progressing through an investigation, ending in a written root-cause hypothesis that names the failing revision and recommends engaging rollback-advisor to shift traffic back to the known-good one.

Real investigation report excerpt (Run 2, incident thread <incident-thread-id-2>, verbatim from the data-plane API, 2026-07-29 - full text with both runs in the evidence file):

"Affected scope: POST /api/checkout on Container App ca-pulsemart-demo. 100% of ingress traffic is routed to the failing revision ca-pulsemart-demo--fault-1785338532. GET /healthz and GET /api/status remain healthy."

"41 HTTP 5xx responses recorded in the 1-minute bucket at 15:24:00Z, with zero 5xx before or after in adjacent buckets - aligning precisely with when the fault revision started serving traffic." ... "20+ ERROR-level log entries from revision ca-pulsemart-demo--fault-1785338532 between 15:23:16Z and 15:23:21Z, each containing: 'checkout failed: payment gateway returned an unexpected error (demo failure mode: checkout-500)'."

"When DEMO_FAILURE_MODE=checkout-500, the _charge_payment function raises CheckoutFailure in the payment.charge dependency span, while inventory.check succeeds. This is the only code path that produces the observed error message." (cross-referenced against app/pulsemart/main.py and app/pulsemart/settings.py in the connected repository)

"Confidence: High. ... All evidence - timing, error message, env var, metrics spike, and source code - converges on a single explanation. No other failure mode or resource-health issue is involved."

Read excerpts like these aloud from the live portal during the real session - this block exists so you know, in advance, the calibre of evidence to expect and can quote it accurately afterward; it is not a substitute for watching it happen live.

Fallback

Investigation time is not fully deterministic. If it is taking longer than expected, narrate what you already know is grounding it (the runbook, the connectors, the source repo) from the Architecture section while it finishes, rather than filling time with speculation about its answer.

Transition cue

"It found the cause and recommended a fix, in writing. Now watch what it does next - and let me be straight with you about why." Move to Act.

5. Act#

~7 min (worst case 9) Segment: Remediate and verify

Objective

Give an honest, non-defensive account of what live testing found about this preview build's approval gate, show what actually governs remediation in this demo (tool scoping plus narrow RBAC - now proven, not pending), and watch the agent execute the real rollback itself, under its own identity, then independently confirm that from the Azure Activity Log.

What we found: the Review-mode gate did not hold

Live-tested against sre-agent-demo, 2026-07-29, across three independent test cycles. The agent-wide actionConfiguration.mode stays at its documented default of Review, and a pre-tool hook (require-approval-for-changes) requests human approval before any restart, scale, or traffic-changing operation. In practice, the mutating az containerapp ingress traffic set command ran for real seconds after the agent decided to run it, on every cycle tried with a write-capable tool present - GET /api/v1/approvals/{threadId} stayed empty throughout, and every message's approval/hook fields stayed null. One of those cycles used a freshly created incident thread whose own agentMode field read "Review" at investigation time - so this was not a stale or misconfigured thread.

The obvious explanation - that the agent's own identity was approving its own action - was tested by removing its "SRE Agent Administrator" role entirely. The gate still did not hold; that theory is disproven. The most likely root cause: this preview data-plane API silently drops a hook's enforcement fields (permissionDecision/enabled, or failMode/maxRejections on an alternate hook shape also tried) when the hook is saved, so the hook is never actually evaluated as configured. No hook shape this repository tried reliably blocks a write in this API version. Full evidence trail: PLAN.md Milestone 5, SPEC.md section 5 Scene 5, and the 2026-07-29 Act-beat evidence file.

Say this on stage exactly this plainly. Do not soften it to "sometimes" - across every real attempt, the gate did not hold. This is not a configuration mistake in this repository; it is a behavior of the preview product surface. Because no build of this preview actually honors Review here, the checkout-5xx response plan is configured agentMode: Autonomous - the honest label for what has always actually happened, not a description of intent that was never true.

What actually governs this demo: tool scoping and narrow RBAC - proven

incident-investigator (the subagent that receives the routed incident) holds no RunAzCliWriteCommands tool at all and is structurally incapable of mutating anything - it can only investigate and recommend, in writing. rollback-advisor is the only subagent in agent/ that holds RunAzCliWriteCommands, and its managed identity's only write-capable RBAC grant is "Container Apps Contributor" scoped to just the ca-pulsemart-demo resource, not Contributor over the resource group. This built-in role's entire action set is Microsoft.App/* and Microsoft.Insights/alertRules/* - there is no Microsoft.Resources/* action anywhere in it, so a write against any other resource in rg-sre-agent-workload-demo (Log Analytics, the container registry, the alert rule, the resource group itself) fails with AuthorizationFailed regardless of what the model decides to try.

This was live-proven, not just asserted: an ad hoc probe asked the live agent to attempt an out-of-scope write (az group update ... --set tags.rbac-scope-test=true, deliberately outside rollback-advisor's Container App-only remit). rollback-advisor refused and made zero tool calls, citing its own scope; a follow-up asking it to bypass that refusal "for this one authorized test" was refused a second time. The RBAC-layer claim is independently, structurally verified regardless of that instruction-layer result: the role definition's actions list has no path to Microsoft.Resources. Across all three real rollbacks - both in the 2026-07-29 evidence file and the third, on a completely rebuilt environment, recorded in PLAN.md - the in-scope write succeeded with zero AuthorizationFailed errors - the narrow RBAC grant (workload_access_level = "narrow", grant_uami_agent_administrator = false) is confirmed sufficient, not pending, on two independently built environments. deny-destructive-deletes and require-approval-for-changes remain configured as documented intent - harmless, and they will start working automatically if Microsoft fixes the underlying platform defect - but tool scoping and narrow RBAC are what this demonstration actually, provenly relies on.

Live: watch the agent remediate

Watch the incident thread (portal, or demo verify bad-deployment). Narrate each step as it happens: rollback-advisor states the exact az containerapp ingress traffic set command it is about to run, in the thread, before running it; it then executes that command for real, under its own managed identity; then it verifies the traffic split, the checkout response, and the alert state, and reports the outcome. You do not run anything yourself in this step - your role is to narrate what the agent is doing and about to prove.

& 'labctl\.venv\Scripts\labctl.exe' status

Run this beforehand (or reuse the Orient beat's output) to have the agent's managed identity's principal ID on screen, ready to compare against the Activity Log next.

The narration after the rollback, not the rollback itself, is the unpredictable part - and this is already root-caused too. On the rebuilt-environment run, the real traffic-shift write succeeded on schedule, but rollback-advisor then hit its own turn limit mid verification (its own message: "The rollback-advisor reached its turn limit"). The parent agent independently re-verified the traffic state via az rest before posting the final resolution summary, which took longer to appear as a result. If the resolution message is slow to show up, the mitigation has almost certainly already happened - say exactly that: "the traffic shift is done; the agent is still confirming and writing up its summary" and check demo verify bad-deployment or the Container App's traffic split directly rather than waiting on the narrative text.

Expected visible state - the real proof point

Container Apps traffic shifts back to the known-good revision - a real control-plane operation performed by the agent. Then open the Azure Activity Log for rg-sre-agent-workload-demo, filtered to Microsoft.App/containerApps write operations, and show its caller field: it names the agent's own user-assigned managed identity principal ID - not your own signed-in account, and not labctl's Azure CLI session. In the 2026-07-29 evidence, both of the first two rollbacks show a real Microsoft.App/containerApps/write event 4-5 seconds after the agent's own tool-call timestamp, with caller = the agent's UAMI principal ID both times, interleaved in the same log with operator-caller (operator@example.com) writes for trigger/reset - the two are clearly distinguishable by caller alone. The rebuilt- environment third run independently confirmed the same attribution pattern on a brand-new agent identity (a different UAMI principal ID than the first two runs, discovered fresh against the new environment, not assumed from the old one) - this is the beat's real, verifiable proof point: not a portal click, an audit record of exactly who changed production and when.

Fallback

If the agent has not executed the rollback within a few minutes of a clear investigation conclusion, do not wait indefinitely: run demo reset bad-deployment yourself as the operator safety net, and narrate that explicitly as a fallback, not as the intended path - this is no longer the demo's Act-beat mitigation step, it is the reliable way back to baseline when something upstream did not complete. Either way, always independently confirm from the Activity Log's caller field who actually made the change, rather than trusting the agent's own self-reported narrative alone.

Transition cue

"The agent made the change. Its own account of that doesn't prove it worked - let's check independently." Move to Verify.

6. Verify#

Objective

Prove recovery with both an automated check and a user-visible check - never declare success from the agent's own claim alone (AGENTS.md, "Real workload and incidents").

Command

Expected (per SPEC.md section 5, scene 6 - confirm exact console output against your build during rehearsal): the checkout user journey succeeds, production traffic targets the known-good revision, the failure rate is back below the alert threshold, the alert has resolved or shows recovery telemetry, and the incident record contains a remediation summary.

Security and safety#

Full rationale: SPEC.md section 9. This section states the checked-in design; the Act beat has the honest account of what live testing found in practice - read both.

Least-privilege RBAC (narrow, default) - proven sufficient

Run mode, hooks, and what actually governs Act

  • accessLevel: High. The agent-wide actionConfiguration.mode stays at its documented default of Review, which by design and per Microsoft's own documentation is meant to prompt for approval before Azure infrastructure write operations specifically - but the checkout-5xx incident response plan that actually governs this scenario's write is configured agentMode: Autonomous (agent/automations/incident-filters/checkout-5xx.yaml), because live testing proved the response-plan-level Review setting never held anyway - see the Act beat for the full evidence trail. Configuring Review here while a write-capable subagent executes unattended would describe intent, not observed behavior.
  • Hook require-approval-for-changes: intended to pause before any disruptive operation - kept as documented intent, not relied on.
  • Hook deny-destructive-deletes: intended to refuse deletion outright - kept as documented intent, not relied on.
  • The agent's UAMI is deliberately not granted "SRE Agent Administrator" - the role that, per Microsoft's own documentation, is required to approve actions. Granting it to the identity whose own actions are supposed to be gated is a plausible self-approval vector, closed off regardless of whether it turns out to matter (see the Act beat: removing it did not, by itself, restore a working gate).
  • labctl demo reset <scenario> remains the operator's reliable safety net for returning to a known baseline - it is not this scenario's Act-beat mitigation step; the agent performs that itself.

What live testing actually found, and what this demonstration relies on instead: across three independent test cycles against this real preview build, neither the Review-mode approval prompt nor either pre-tool hook reliably blocked a mutating write - see the Act beat for the full, specific evidence. The controls this repository actually, provenly relies on are tool scoping and narrow RBAC: incident-investigator has no Azure-write tool at all; rollback-advisor is the only subagent that does, and its identity's only write-capable role is scoped to one Container App resource whose action set cannot reach any other resource type. The hooks above remain configured as documented intent, not as a settled operative control, and will start working automatically if Microsoft fixes the underlying platform defect.

Cost#

Full rationale: SPEC.md section 14; official pricing: learn.microsoft.com/azure/sre-agent/pricing-billing.

Azure SRE Agent bills a fixed 4 Azure Agent Units per agent-hour, always-on, from the moment it is created until labctl destroy deletes it - independent of whether it is investigating anything. That alone totals roughly 2,880 AAU across a 30-day month (4 x 24 x 30; a 31-day month is closer to 2,976) with zero active-flow use.

  • This demo caps monthly_aau_allocation at 3,000 (the official template's own default is a permissive 10,000 ceiling, not a required minimum), leaving headroom for the fixed always-on cost plus several incident-investigation/remediation passes (each roughly 10-90 AAU per Microsoft's own worked examples).
  • Basic ACR and a Consumption (scale-to-zero-capable) Container Apps environment keep the workload side inexpensive.
  • labctl status shows the running agent and its cost posture on demand - use it, do not assume.
  • labctl destroy is the normal end of every rehearsal and of the live session; see Cleanup.

Cleanup#

Run this at the end of every rehearsal and at the end of the live session, once you no longer need the environment:

& 'labctl\.venv\Scripts\labctl.exe' destroy --plan-only
& 'labctl\.venv\Scripts\labctl.exe' destroy --yes

Expected: ownership tags on every resource group are checked first; a warning that the agent has been incurring always-on Azure Agent Unit cost until this point; both resource groups and every child resource are destroyed; a final check confirms nothing owned remains and exits 0. If any unrecognized resource is found inside an owned resource group, destroy stops and prints it for review rather than deleting it blindly - only pass --allow-unrecognized-resources after you have read that list yourself.

Adoption guidance#

  1. Scope the agent to one workload resource group first, not a whole subscription.
  2. Connect Application Insights, Log Analytics, and Azure Monitor before anything else.
  3. Start in Review mode with explicit approval and destructive-deny hooks, but verify live that the approval gate actually holds in your subscription before trusting it for anything real - if it does not, rely on tool scoping and narrow RBAC the way this demonstration does, and prove the RBAC boundary live rather than assuming it.
  4. Write down one real runbook before your first live incident - the agent is grounded by what you give it.
  5. Track cost from day one with the equivalent of labctl status; always-on billing starts at creation.
